# ADR 0009: Multi-Cloud Core Portability — Spry on Google Cloud

## Status
Accepted (Architecture & IaC definition; core portability validated without live GCP billing)

## Context
Through Labs 3–8, Spry (WCA Badge Generator) runs on AWS using CloudFormation (`infra/backend.yml`, `infra/frontend.yml`) and Terraform managed via HCP Terraform (`infra/auth.tf`, `infra/reports.tf`, `infra/ai.tf`). As an architectural exercise (Lab 9), we evaluate migrating Spry's core—the static frontend, FastAPI container API, and PostgreSQL database—to Google Cloud Platform (GCP), while deciding which surrounding services (authentication, async weekly reports, and LLM agenda parsing) should be replaced, kept on AWS in a multi-cloud topology, or dropped.

## Key Architectural Questions Answered

### 1. The Database Choice: Latency, Cost, and Code Impact
We evaluated four options for Spry's PostgreSQL database (`Competitor`, `Role`, `BadgeTemplate`, `User`, `Meeting`):
1. **Cloud SQL (`db-f1-micro`) running 24/7:** Zero code changes (SQLAlchemy async + `asyncpg` + Alembic work unchanged), sub-2 ms in-region latency to Cloud Run in `us-central1`, but costs **$9.37/month** ($7.67 compute + $1.70 for 10 GB SSD) even with zero users because Cloud SQL does not auto-pause.
2. **Cloud SQL (`db-f1-micro`) stopped when idle (Selected for `gcp/`):** Same zero code changes and low in-region latency when running. Setting `activation_policy = "NEVER"` via Terraform or `gcloud sql instances patch` stops compute billing ($0/hr), leaving only **$1.70/month** for 10 GB SSD storage. Trade-off: operational step (or Cloud Scheduler + Cloud Run/Function trigger) to start the instance, with ~60–90 seconds startup latency before serving requests.
3. **Firestore (Serverless NoSQL):** Drops monthly bill to **$0.00/month** under student traffic (50,000 reads/day, 20,000 writes/day, 1 GiB free) with single-digit ms latency and true scale-to-zero. Trade-off: requires rewriting the entire SQLAlchemy/Alembic relational data layer into document collections, denormalizing `Role` ↔ `Competitor` links, and carefully bounding list queries so a single page load doesn't burn the 50k daily read quota.
4. **Keep Aurora Serverless v2 on AWS and connect cross-cloud from GCP Cloud Run:** Zero GCP DB cost ($0.10–$0.30/mo on Aurora when paused), zero SQL rewrites, but introduces **~30–80 ms cross-cloud network RTT per SQL query** (`us-central1` ↔ `us-east-1`), **AWS internet data egress fees (~$0.09/GB)**, and security exposure (either opening Aurora publicly over TLS or paying for a VPN/NAT tunnel, plus Aurora's 15-second cold wake-up still hits the first request).

**Conclusion:** For core migration without rewriting the ORM, **Cloud SQL stopped when idle** is the cleanest architectural choice; if long-term $0/month idle relational-free hosting were the sole priority, **Firestore** would win at the cost of rewriting `backend/app/models/` and `backend/app/api/`.

### 2. Email Provider & Secret Management
Google Cloud has no native transactional email service comparable to Amazon SES.
- **Selected approach:** Keep **Amazon SES** on AWS for the async weekly report mailer (`infra/reports.tf`), since `kastranets.pn@ucu.edu.ua` is already verified and SES costs $0.10 per 1,000 emails.
- **If reports were moved to GCP:** We would use **SendGrid** (free tier: 100 emails/day) or **Resend** via HTTPS REST API from Cloud Run. Its API key would live exclusively in **Google Cloud Secret Manager** (`google_secret_manager_secret`), mounted into the Cloud Run service as a secret environment variable and readable only by the dedicated `spry-api-runtime` service account (`roles/secretmanager.secretAccessor`)—never in git, `.tfvars`, or container images.

### 3. Features Kept on AWS (Not Moved) and Why
We intentionally do **not** migrate three subsystems in `gcp/`:
1. **Weekly Report Pipeline (`infra/reports.tf`):** Depends on Amazon SES (no GCP equivalent) and private S3 + VPC Lambda split; already costs ~$0.00/month on AWS and gains nothing from a rewrite to Cloud Scheduler + Pub/Sub + SendGrid.
2. **AI Agenda Parser (`infra/ai.tf`):** Uses Amazon Bedrock (`anthropic.claude-opus-5-5`) with IAM role auth. GCP's $300 Free Trial excludes Vertex AI partner models (Claude) and AI Studio Gemini billing, so keeping it on AWS avoids both credit restrictions and duplicate API key management.
3. **Authentication (`infra/auth.tf`):** Amazon Cognito (`us-east-1_T7FaZwE2p`) already holds user records, Managed Login v2 styling, and Google IdP configuration. Migrating users to Identity Platform requires reconfiguring OAuth redirect URIs and migrating user tokens with zero user-facing benefit during a partial cloud move.

## Consequences
- **State Isolation:** `gcp/` maintains a separate Terraform configuration and state from `infra/` so GCP changes cannot inadvertently modify or destroy AWS resources.
- **Portability Achieved:** Removing the Lambda-only entrypoint assumption from `backend/Dockerfile` (`PORT` env var support) makes the backend container portable across Cloud Run, local Docker, ECS, or Kubernetes.
- **Cleanup Discipline:** Any live Cloud SQL instance created from `gcp/` must be stopped (`db_activation_policy = "NEVER"`) or destroyed (`terraform destroy`) immediately after verification to prevent ongoing hourly/storage charges.
